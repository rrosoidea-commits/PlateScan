# Project Overview

## What the project is
An **automatic license plate recognition (ALPR)** system built as a two-stage computer vision pipeline:

```
Image ─► [Stage 1: YOLO26n plate detector] ─► plate bounding box ─► crop ─► [Stage 2: OCR reader] ─► "ABC1234"
```

1. **Detection** — locate every license plate in a photo and return its bounding box and confidence.
2. **Recognition** — read the characters on each detected plate and return them as text.

## Core objective
- Train a plate detector that is **accurate**, **fast enough for real-time use**, and **small enough to run on a consumer laptop GPU**.
- Attach a reader that turns each detected plate into text, and **measure both stages objectively**.

## Problem it solves
Manually reading plates from camera footage or photos is slow, error-prone, and does not scale. An ALPR system automates this for use cases such as:
- **Parking and gate access control** (match a plate against an allow-list),
- **Traffic monitoring** and toll collection,
- **Security and incident review** (search footage for a specific plate).

The detector removes the need for fixed camera angles or manual cropping; the reader converts the result into searchable text.

# Implementation Journey

A chronological record of what was done, from data ingestion to a working end-to-end pipeline.

### 1. Environment setup
- Started as a Jupyter notebook; **moved to a plain Python script** (`AI_PlateNumber.py`) organized as numbered functions (`Part 1` … `Part 10`) called from `main()`.
- Found that the installed PyTorch was a **CPU-only build** (`2.14.0+cpu`) although the laptop has an NVIDIA GPU → Part 1 now detects this and installs the **CUDA 12.8 build** before importing PyTorch.
- Installed Ultralytics **8.4.204** (YOLO26 requires ≥ 8.4.0).

### 2. Data ingestion and configuration
- Loaded the Roboflow export (`train/`, `valid/`, `test/`, `data.yaml`).
- **Rewrote `data.yaml`** with an absolute `path:` and relative split paths (Roboflow's `../train/images` paths depend on the launch folder); the original was backed up as `data_original.yaml`.

### 3. Dataset sanity check
- Counted images, label files and boxes per split; checked for missing/empty labels; measured plate sizes at the 640 px training resolution.
- **Inspected 6 random training images** with their boxes drawn to verify annotation quality.

### 4. Training-pipeline smoke test
- Ran a **1-epoch test on 2% of the data** before committing to a multi-hour run. It exposed two problems (see *Engineering Hurdles*): a **memory crash** with 4 data-loading workers, and **~800 images silently rejected** due to mixed label formats.
- Both were fixed (workers → 1; new **Part 2b** label repair) and the smoke test was re-run successfully.

### 5. Full training run
- YOLO26n, 640 px, **50 epochs**, patience 15, seed 42, batch 8, default augmentations.
- Completed all 50 epochs in **4.42 hours**; best checkpoint at **epoch 47**.
- Re-running the script **skips training** if `best.pt` exists (`RETRAIN` / `RESUME` flags control this).

### 6. Evaluation of the detector (Parts 6–10)
- **Training curves** analysed for overfitting and plateau.
- **Test-split evaluation** (593 images never used for training decisions): precision, recall, F1, mAP, confusion matrix, PR curve.
- **Error analysis:** every test prediction matched to ground truth (IoU ≥ 0.5) to count hits, misses and false positives; 8 examples visualized, including 4 failures.
- **Speed benchmark:** single-image inference on all 593 test images.
- **Report artifacts** saved to `plate_detection/outputs/` (weights, figures, `metrics.json`, `metrics_summary.csv`).

### 7. Plate reading (OCR) — `AI_PlateNumber_OCR.py`
- **v1 — EasyOCR** with grayscale, contrast enhancement (CLAHE) and resizing → poor results (**1/23** plates exact).
- **v2 — tuned EasyOCR:** systematic comparison of preprocessing variants on **23 hand-labeled crops** → median filter, 160 px height, beam-search decoding (**7/23** exact, 74% characters).
- **Evaluated an external character dataset** (*YOLOCR Single character*, 360 images) for training a custom reader → **rejected** as insufficient (see *Engineering Hurdles*).
- **v3 — fast-plate-ocr** (plate-specific pretrained model) → **20/23** exact, **98%** characters, **~30× faster** than EasyOCR. Adopted as the default engine (`OCR_ENGINE` setting keeps EasyOCR available for comparison).
- Ran the full pipeline on all 593 test images and generated a **50-plate manual-check sheet** for an unbiased OCR accuracy measurement.

### 8. Documentation
- `pipeline_diagram.svg` — visual summary of preprocessing, training and outputs.
- This document.

> **Deployment status:** the pipeline runs locally from the command line on single images, folders, or the test set. A web interface (e.g., Streamlit upload page) has been designed but **not yet built**; see *Future Roadmap*.

# Methodology & Architecture

## 1. Dataset

| Split | Images | Share | Plates (boxes) | Empty labels (background) |
|---|---|---|---|---|
| Train | 15,160 | 89.7% | 18,323 | 8 |
| Valid | 1,155 | 6.8% | 1,403 | 0 |
| Test | 593 | 3.5% | 743 | 2 |
| **Total** | **16,908** | 100% | **20,469** | 10 |

- **Single class:** `license`.
- **Plate size at 640 px:** median height **118 px**; only **292 of 20,469** plates (1.4%) are under 20 px tall. The test set has a larger share of tiny plates (**3.6%**) than train (1.4%).
- **Contents:** mostly US-style vanity and standard plates, some Philippine and other regional plates, and a small number of synthetic (AI-generated) images.

## 2. Preprocessing

### Applied by Roboflow at export (fixed, stored on disk)
- **Auto-orientation** (EXIF rotation applied, then stripped).
- **Resize to 640×640 (stretch)** — aspect ratio is not preserved.
- **Offline augmentation, 3 versions per training source image:**
  - rotation ±15°, brightness ±15%, exposure ±10%,
  - Gaussian blur 0–2.5 px, salt-and-pepper noise on 0.1% of pixels.

### Applied in this project
- **Configuration repair:** absolute dataset root in `data.yaml`.
- **Label repair (Part 2b):** 797 label files mixed polygon rows and box rows; polygon rows were converted to their axis-aligned bounding boxes (clipped to the image). Originals kept in `labels_original/`. Verified on a copy: **identical boxes, idempotent**.
- **Normalization / encoding** (YOLO format): each label row is `class x_center y_center width height`, all scaled to 0–1; pixel values scaled to 0–1 by the data loader; single class encoded as index 0.
- **Split:** kept exactly as exported (no re-splitting).

### Online augmentation during training (Ultralytics defaults)
| Augmentation | Setting | Purpose |
|---|---|---|
| **Mosaic** | 1.0 (always) | Combines 4 images → more plates per step, more scale variety |
| **close_mosaic** | last 10 epochs | Final epochs on natural-looking images |
| **HSV** (hue/sat/value) | 0.015 / 0.7 / 0.4 | Lighting and color robustness |
| **Horizontal flip** | 0.5 | Viewpoint variety (acceptable for detection, not for OCR) |
| **Translate / scale** | 0.1 / 0.5 | Position and size variety |
| Rotation, shear, perspective, mixup | off | — |

## 3. Detection model — YOLO26n

- **Architecture:** Ultralytics **YOLO26 nano** — single-stage, anchor-free detector; **2,389,735 parameters**, 5.4 GFLOPs (fused).
- **NMS-free design:** YOLO26 predicts final boxes directly, so its box loss uses an **L1 term** instead of the DFL loss seen in older YOLO versions.
- **Transfer learning:** initialized from **COCO-pretrained** weights; the network already recognizes edges, shapes and objects and only adapts to the plate class.
- **Losses:** box regression loss, classification loss, L1 coordinate loss.

| Hyperparameter | Value | Reason |
|---|---|---|
| Image size | 640 | Matches dataset export resolution |
| Epochs / patience | 50 / 15 | Upper bound with early stopping on val mAP |
| Batch size | 8 | Fits a 4 GB GPU (1.3 GB used) |
| Workers | 1 | Memory limit on an 8 GB RAM laptop |
| Seed / deterministic | 42 / on | Reproducibility |
| Optimizer, learning rate, augmentation | Ultralytics defaults | No hyperparameter search was performed |

- **Model selection:** `best.pt` = epoch with the highest validation mAP@0.5:0.95 (**epoch 47**).

## 4. Recognition model — fast-plate-ocr

- **Model:** `cct-xs-v2-global-model` — a **Compact Convolutional Transformer** trained only on license plate crops from ~65 countries; runs with **ONNX Runtime on the CPU**.
- **Input:** RGB plate crop (detector box + 5% margin), resized internally to 128×64.
- **Output:** 10 fixed character slots, each predicting `0–9`, `A–Z`, or *empty*; text = non-empty slots; per-character confidences averaged into a plate confidence. It also predicts the plate's **country/region**.
- **Why no extra preprocessing:** median filtering made no difference for this model (98.0% with or without).
- **Alternative kept for comparison:** EasyOCR (CRAFT text detector + CRNN recognizer) with median filter, 160 px resize, beam search, and a "largest text only" rule to discard slogans and state names.

## 5. Evaluation methodology

| Stage | Metric | How it is computed |
|---|---|---|
| Detector | Precision, Recall, F1 | Ultralytics validator on the **test** split, at the F1-optimal confidence |
| Detector | mAP@0.5, mAP@0.5:0.95 | Area under the PR curve; averaged over IoU 0.5–0.95 for the stricter metric |
| Detector | TP / FP / FN counts | Greedy matching, confidence ≥ 0.25, IoU ≥ 0.5 |
| Detector | Speed | Batch size 1 over 593 test images after 10 warm-up images |
| OCR | Plate accuracy | Exact string match after uppercasing and removing non-alphanumerics |
| OCR | Character accuracy | 1 − (Levenshtein edit distance ÷ true length), i.e., 1 − CER |

> **Note:** the dataset contains **no plate-text labels**, so OCR accuracy was measured on **23 crops labeled by hand** during development. A separate **50-plate sample** (`manual_check.csv`) is reserved as an unbiased final measurement.

# Engineering Hurdles & Struggles

### 1. GPU not used — CPU-only PyTorch
- **Symptom:** `torch.cuda.is_available() == False` despite an RTX 2050.
- **Cause:** PyTorch `2.14.0+cpu` was installed.
- **Fix:** Part 1 checks the installed build **before importing torch** (Windows locks loaded DLLs) and installs the CUDA 12.8 wheels. Result: PyTorch `2.11.0+cu128` with GPU support.

### 2. Missing YAML library
- **Symptom:** `import yaml` failed.
- **Cause:** Ultralytics 8.4.x no longer depends on PyYAML.
- **Fix:** switched to Ultralytics' built-in `YAML.load` / `YAML.save`; verified a round-trip on the real file (including a Windows path with spaces).

### 3. Memory exhaustion during training (Windows)
- **Symptom:** `OSError: [WinError 1455] The paging file is too small`; Windows logged two *low virtual memory* events; the desktop wallpaper and icons disappeared until Explorer was restarted.
- **Cause:** on Windows, every data-loading worker process loads its own copy of PyTorch + CUDA (~1 GB each), and validation spawns **2× the worker count**. With 4 workers: main process ~5 GB + 11 workers ~1 GB each on a 7.8 GB RAM machine.
- **Fix:** `WORKERS = 1`, verified with a smoke test (free virtual memory stayed ≥ 2.6 GB) **at no measurable speed cost** (~6 iterations/s either way, GPU-bound). Also added the `if __name__ == "__main__":` guard required for Windows multiprocessing.

### 4. ~800 images silently dropped — mixed label formats
- **Symptom:** in the smoke test, 48 of 303 sampled images were reported as *"ignoring corrupt image/label: labels mix segment and detection rows"*; validation counted 1,104 instead of 1,155 images.
- **Cause:** the merged dataset contains files with both polygon rows and box rows; Ultralytics rejects such files entirely.
- **Scope:** 711 train, 51 valid, 35 test files (**4.7%**, 2,779 plates).
- **Fix:** Part 2b converts polygon rows to boxes **only in mixed files**, backs up originals, and clears the label cache. After the fix: **0 corrupt**, all 1,155 validation and 593 test images used.

### 5. Long training on modest hardware
- **Constraint:** ~5.5 minutes per epoch → **4.42 hours** for 50 epochs.
- **Mitigation:** smoke tests before the full run; `RETRAIN`/`RESUME` flags and automatic skip when `best.pt` exists so later parts run in ~2 minutes; guidance to reduce batch size rather than images if memory is tight.

### 6. Poor initial OCR accuracy
- **Symptom:** EasyOCR v1 read **1 of 23** labeled plates correctly (56% characters); common errors were look-alike characters, extra frame/slogan text, and failures on noisy crops.
- **Cause:** general-purpose OCR + Roboflow's salt-and-pepper noise; CLAHE contrast enhancement amplified the noise.
- **Mitigation:** controlled experiments (8 preprocessing variants × 2 decoders × 4 text-selection rules) → median filter + larger crop (7/23); then a **plate-specific model** (20/23).

### 7. Unsuitable character dataset
- The candidate *YOLOCR Single character* dataset was evaluated for training a custom reader and **rejected**:
  - only **360 images / 672 characters**, **11–29 examples per class**, no validation/test split,
  - images are close-ups of 1–4 characters rather than full plates (domain mismatch),
  - visible neighbouring characters left **unlabeled**,
  - mostly UK-style plates and fonts.

### 8. Tooling friction
- VS Code's language server pointed to a different Python interpreter, producing false *"import could not be resolved"* warnings.
- ONNX Runtime printed harmless *"Error merging shape info"* warnings → silenced via logger severity.
- EasyOCR's beam-search decoder emits a rare numeric-overflow warning (harmless).

> **No convergence problems were observed:** validation loss decreased steadily and ended at its minimum (no overfitting); mAP plateaued in the last 10 epochs (+0.007 mAP@0.5:0.95).

# Limitations & Trade-offs

### Detector
- **Tiny and distant plates** are the main source of misses (44 missed of 743 test plates). Test recall (**0.926**) is lower than validation recall (0.956), consistent with the test set's higher share of tiny plates.
- **Possible train/test overlap:** 243 of 385 test source-photo names also appear in the training set (Roboflow distributes augmented copies across splits). Some may be unrelated photos sharing a name, but **test scores may be optimistic** for truly unseen images.
- **Inconsistent annotation style:** some labels box only the characters, others the whole plate frame. Correct detections can therefore count as both a miss and a false positive, and **mAP@0.5:0.95 (0.792) is depressed** by box-style disagreement.
- **Stretched training images:** Roboflow's stretch resize distorts aspect ratios, whereas inference letterboxes real images → a small train/inference mismatch.
- **Synthetic noise in evaluation:** many test images carry Roboflow's added noise, which does not reflect clean real-world camera feeds (in either direction).

### Reader (OCR)
- **Accuracy measured on a small sample:** 20/23 exact on crops large enough to be read by eye. Accuracy on tiny or heavily degraded plates is lower; the 50-plate manual check is still pending.
- **Remaining character confusions:** Q↔O, D↔B; small auxiliary marks (e.g., a county number) can be read as extra characters.
- **No plate-format validation:** a read is not checked against a country's plate pattern.
- **Region prediction** covers ~65 countries but **not the Philippines**.
- **Mirrored plates** (from flip augmentation in the source data) cannot be read correctly.

### System and computational
- **Hardware-bound training:** 4 GB VRAM and 8 GB RAM limit batch size and data-loading parallelism; a larger model (`yolo26s`) would train considerably slower.
- **Single-image pipeline:** no video tracking, so each frame is read independently (no multi-frame voting).
- **Local only:** no web interface, API, authentication or storage layer yet.
- **Privacy:** license plates are personal data; any deployment needs consent, retention and access controls.

### Trade-offs made deliberately
| Decision | Gain | Cost |
|---|---|---|
| YOLO26**n** instead of larger variants | 62 FPS on a laptop GPU, 5.3 MB model | Some accuracy on small plates |
| Default hyperparameters | Reproducible, time-efficient | Possible missed gains from tuning |
| `WORKERS = 1` | Stable on 8 GB RAM | Less headroom on faster GPUs |
| Pretrained OCR instead of training one | No text labels needed, 98% characters on readable plates | Not specialized to local plate formats |
| Two-stage pipeline | Each stage replaceable and measurable | Two models to maintain |

# Advantages & Business Value

- **Strong detection quality** — test precision **0.985** means almost every reported plate is real; **F1 0.955** overall.
- **Real-time on consumer hardware** — **62 FPS** detector and **42 FPS** full pipeline on an entry-level laptop GPU; OCR adds only **~3 ms per plate on the CPU**.
- **Lightweight artifacts** — detector **5.3 MB**, OCR model a few MB → suitable for edge devices and low-cost deployment.
- **Minimal labeling cost** — transfer learning for detection (boxes only) and a **pretrained plate reader** (no character or text labels) avoided building an OCR dataset.
- **Modular two-stage design** — the detector and reader are evaluated and upgraded independently (e.g., EasyOCR → fast-plate-ocr was a configuration change, `OCR_ENGINE`).
- **Evidence-based engineering** — every major choice was measured: smoke tests before long runs, a labeled comparison set for OCR (1/23 → 7/23 → 20/23), and automated error analysis.
- **Data quality safeguards** — automatic detection and repair of mixed label formats prevented a **4.7% silent data loss**, including test images.
- **Reproducible and report-ready** — fixed seed, deterministic training, skip/resume logic, and automatic export of weights, figures, JSON and CSV metrics.
- **Open-source stack** — Ultralytics, PyTorch, ONNX Runtime and fast-plate-ocr: no licensing fees.

**Compared with alternatives:**
| Alternative | Drawback addressed by this approach |
|---|---|
| Classical CV (edge/contour plate finding) | Fragile under lighting, angle and clutter; no learned robustness |
| General OCR on the full image | Reads every sign and sticker; slow; poor on small plates |
| End-to-end single model (detect + read) | Requires plate-text labels for every image; harder to debug and improve |
| Commercial cloud ALPR APIs | Per-request cost, internet dependency, data leaves the premises |

# Future Roadmap

### Short term (measurement and quality)
- **Complete the 50-plate manual OCR check** and report plate accuracy and character error rate (CER).
- Add **end-to-end recognition rate** (plates both detected and read correctly), **accuracy within 1 character**, and a **confidence-threshold table** (coverage vs. accuracy).
- **Plate-format rules** for the target country (e.g., Philippine `ABC 1234`) to correct O↔0, I↔1, B↔8, S↔5 by position.
- **Reject low-confidence reads** ("unreadable — please retake") instead of guessing.

### Model improvements
- Train **YOLO26s** and compare in `metrics_summary.csv` (accuracy vs. speed).
- **Re-split the dataset by source photo** to eliminate train/test overlap and obtain an unbiased test score.
- **Standardize box style** (full plate vs. characters) to raise mAP@0.5:0.95 and crop consistency.
- Increase input resolution or use tiling for **small/distant plates**.
- **Fine-tune the OCR model on local plates** (crops labeled with their text) for regional fonts and formats.

### Product and deployment
- **Web interface** (Streamlit): upload photo → annotated image + plate text + confidence; EXIF-orientation handling; models cached in memory.
- **Video support** with object tracking and **multi-frame voting** for stable reads.
- **Export to ONNX / TensorRT** for faster inference and edge devices (e.g., Jetson).
- **Allow-list / watch-list matching** and a database of read events for access-control use cases.
- **Privacy safeguards:** local processing, retention limits, access logs, and plate masking in stored images.
